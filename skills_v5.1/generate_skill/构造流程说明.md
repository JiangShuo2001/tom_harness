# skills_v5 构造流程说明

`skills_v5/generate_skill` 是一个以 LLM 为核心的 skill 生成流程，用来从统一的社会心智框架中生成可直接落地的 skill 库。

当前生成流程默认读取英文框架文件 `social_mind_skill_framework_en.md`。中文框架文件 `../social_mind_skill_framework_text.md` 和 `.svg` / `.jpg` 图像用于人工核对，不作为默认机器输入。

## 一、流程目标

这个流程的目标不是简单批量产出条目，而是生成一套：

1. 结构清晰的微观 skill。
2. 可直接路由的宏观 skill。
3. 每个 skill 都有明确能力变量、边界和可解释性。
4. 生成结果同时覆盖 benchmark 能力和真实社会场景能力。
5. 生成的 registry、unit pack 和 `SKILL.md` 均使用英文。
6. API 调用固定使用 `client.chat.completions.create(...)` 风格，不再通过额外的 API 模式变量切换协议。
7. `run` 使用独立的默认超时与 token 预算；`plan` 是本地解析，不再调用 LLM。
8. **L0 元控制层是横切层**：`micro-01..04` (任务路由 / 证据链 / 多解释竞争 / 反偏误检查) 对所有 macro 隐式生效，**不应出现在任何 macro 的 `expandable_micro_ids` 列表中**。它们是路由器和质量控制层，由调度器在解任意 macro 前/中调用，不是 macro 的可选诊断挂载。生成与审计流程应强制此约束。

当前版本对应 `56 + 20` 的框架：

- `micro-01` 到 `micro-56`
- `macro-01` 到 `macro-20`

## 二、输入层

流程依赖四类核心输入：

1. `social_mind_skill_framework_en.md`
   - 英文权威定义 56 个微观 skill 和 20 个宏观 skill 的名称、核心变量、边界与宏观展开关系。
   - 生成 registry 和 unit pack 时都必须以它为准。
2. `skill_blueprint.json`
   - 定义 skill 总数、分层结构、设计原则、宏观原型、文档 schema。
   - 宏观原型使用具体 `expandable_micro_ids`，不再只使用主题标签。
3. `prompts/`
   - `00_plan.md`：生成 registry。
   - `01_micro.md`：生成微观 skill pack。
   - `02_macro.md`：生成宏观 skill pack。
   - `03_audit.md`：审计覆盖、重叠、边界和膨胀风险。
   - `04_validation.md`：生成验证集。
   - `05_feedback.md`：根据 traces 生成候选反馈补丁。
4. 参考资料
   - `../social_mind_skill_framework_text.md`
   - `../social_mind_skill_framework.svg`
   - `../social_mind_skill_framework.jpg`

## 三、核心构造步骤

### 1. 生成 registry

先根据英文框架文本和蓝图生成完整 registry，确定每个 unit 的：

- id
- level
- layer
- family
- title
- core_question
- decision_variable
- use_when / do_not_use_when
- boundary_neighbors
- source_mix

registry 必须遵守 `social_mind_skill_framework_en.md` 中的 id、标题、核心变量和边界；宏观 skill 必须保留具体 `micro-xx` 展开列表。

### 2. 展开 micro pack

对每个 `micro-xx`，LLM 会生成 compact pack，重点包括：

- one-sentence description
- use when / do not use when
- decision variable
- trigger checklist
- workflow
- boundary exit rule
- references / minimal pair / failure modes

微观 skill 的核心是：

- 对焦一个具体能力变量。
- 尽量低重叠。
- 便于诊断、解释和修复。

### 3. 展开 macro pack

对每个 `macro-xx`，LLM 会生成宏观场景型 pack。

宏观 skill 的特点是：

- 它不是 micro 的简单拼接。
- 它可以直接路由到一个典型场景。
- 当场景高度匹配时，可以直接调用宏观 skill 完成推理。
- 当需要补充诊断时，再展开 `expandable_micro_ids` 中的具体 micro。

### 4. 审计

审计层主要检查：

- 覆盖是否完整。
- 宏观原型是否清晰。
- 微观 skill 是否过度重叠。
- 边界是否模糊。
- 是否有膨胀风险。
- L0 元控制能力是否足够。
- 宏观 skill 是否仍使用具体 micro id，而不是松散主题标签。

审计输入按合法 JSON 分块传入，不再按字符截断 JSON。

局部 `--only` 生成默认不做完整库审计，避免把未生成的 unit 误报为覆盖缺口。需要时可使用 `--audit-partial` 只审计本次生成的子集。

### 5. 验证

验证阶段会为每个 unit 生成小型验证集，包括：

- 正例。
- 近邻误判例。
- 边界例。

验证集会做代码级检查：每包必须有 3 到 5 条，必须包含正例和近邻/边界例，且 `gold_answer` 必须匹配 `labels` 中的一个标签。

### 6. 反馈候选

流程会根据 audit 结果和 traces 生成候选补丁，但只是候选，不会自动回灌。

这里强调两点：

- 好的推理路径可以被保留为流程性步骤。
- 错误路径可以转化为边界警告或 shortcut warning。

### 7. 人工批准后应用

候选补丁需要人工审批后才会写回 unit。

流程不会自动把反馈灌回 skill 文件，也不会自动冻结版本。

补丁应用阶段有代码级白名单，只允许修改 `use_when`、`do_not_use_when`、`trigger_checklist`、`workflow`、`boundary_exit_rule` 和指定的 `references.*` 字段，避免审批文件误改 id、level 等结构字段。

### 8. 冻结

冻结只在人工确认后进行，用来固化一个被审核过的版本快照。

## 四、当前设计原则

1. 微观 skill 以能力变量为中心。
2. 宏观 skill 以场景原型为中心。
3. 英文框架文本是生成流程的权威来源。
4. 蓝图是机器可读的生成约束。
5. 宏观展开使用具体 `expandable_micro_ids`。
6. 审计层独立存在，用于发现重叠、缺口和膨胀。
7. 反馈与冻结必须人工批准。
8. 不保留旧式 `skill1..skill68` 壳底命名。

## 五、输出结果

一次完整运行通常会产出：

- `skill_registry.json`
- 各 unit 的 `SKILL.md`
- 各 unit 的 `unit_pack.json`
- `references/examples.md`
- `audit_report.json`
- 可选 `validation_items.json`
- 可选 `feedback_candidates.json`
- 可选 `approval_template.json`

## 六、适用方式

这个流程适合两类用途：

1. 从零生成一套完整 skill 库。
2. 在已有运行结果上做增量验证、审计和选择性反馈。

它的核心不是“堆更多 skill”，而是把 skill 做得更能解释、更能路由、更能对齐真实社会心智问题。
